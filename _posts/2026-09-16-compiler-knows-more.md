[Part 1: The 6502 timing DSL]({{ '/blog/timing-is-data/' | relative_url }}) described the DSL that generates the MyNES 6502 core. The same compiler generates the functions that the DMC sample fetch uses to find out what the CPU does on its next cycle.

## The DMC sample fetch

The NES audio chip (APU) has a delta modulation channel (DMC) that plays 1-bit audio samples read directly from cartridge ROM. When the DMC needs a sample, it halts the CPU and takes over the bus for 3 or 4 cycles. The halt comes in the middle of an instruction, for example between cycle 3 and cycle 4 of whatever the CPU was executing.

The DMA controller needs 3 facts about the CPU's next cycle to work correctly:

1. The address the CPU reads next. The bus does not float while the CPU is halted, and the DMA controller re-reads from the address the CPU was about to drive. Those reads have side effects: reading $2002 clears the VBL flag, reading $2007 increments the VRAM pointer, and reading $4015 clears the frame IRQ.
2. Whether the next cycle is a read or a write. The hardware cannot halt the CPU during a write cycle, so the DMA waits.
3. Whether the next cycle is a SHA/SHX/SHY dummy read. These unofficial store instructions compute their store value from the high byte of the target address. When the DMA halts the CPU on the dummy-read cycle right before the write, the address corruption changes: the `(ADH+1)` AND term drops out.

An emulator can answer these questions with hand-written logic. Someone reads the CPU code, works out which instructions read from which address on which cycle, and writes a second state machine that encodes the answers. That state machine goes out of date when the CPU timing changes, and the CPU and the DMA fall out of sync.

## Functions generated by the DSL compiler

The DSL compiler already has the data for all 3 answers. During code emission it classifies every microcode step by bus operation (read, write or dummy read) and records which steps contain SHA-family fixup operations. From this it generates 3 pure functions, each one switch statement.

This is an excerpt of the generated `cpu_get_next_read_addr()` in `cpu_gen.c`:

```c
uint16_t cpu_get_next_read_addr(CPU *cpu) {
    switch (cpu->uPC) {
    case 0: return cpu->PC;
    case 1: return cpu->PC;
    case 5: return 0xFFFA;
    case 6: return 0xFFFB;
    case 22: return cpu->PC;
    case 23: return cpu->PC;
    case 24: return ((uint16_t)cpu->ADH << 8) | cpu->ADL;
    // ... 600+ more cases
    }
}
```

Each case matches the current microcode PC and returns the exact address the CPU would drive on its next cycle. Case 0 (the fetch state) would read from PC. Case 24 (the second cycle of `lda-zp`) would read from the effective address in ADH:ADL. The compiler has this address because it already emitted the code that does the read.

`cpu_next_is_write()` is a switch of the same kind. It returns true for every uPC value whose next cycle writes:

```c
bool cpu_next_is_write(CPU *cpu) {
    switch (cpu->uPC) {
    case 2: return true;    /* nmi-handler: push PCH */
    case 3: return true;    /* nmi-handler: push PCL */
    case 4: return true;    /* nmi-handler: push P */
    case 76: return true;   /* sta-zp: store */
    case 314: return true;  /* inc-zp: write old value */
    case 315: return true;  /* inc-zp: write new value */
    // ...
    default: return false;
    }
}
```

`cpu_next_is_sha_dummy_read()` returns true for exactly 5 microcode steps, the cycles where SHA, SHX, SHY and TAS perform their page-crossing dummy reads:

```c
bool cpu_next_is_sha_dummy_read(CPU *cpu) {
    switch (cpu->uPC) {
    case 815: return true;
    case 819: return true;
    case 824: return true;
    case 828: return true;
    case 832: return true;
    default: return false;
    }
}
```

The compiler derives all 3 functions from the DSL. Adding or changing an instruction updates the DMA helpers automatically. The CPU timing specification and the DMA interaction rules are the same data, so they cannot drift out of sync.

## How `nes_step()` uses the functions

This is the DMC DMA implementation in `nes.h`, lines 513 to 550:

```c
if (apu_dmc_needs_sample(&nes->apu) && nes->cpu.rdy
    && !cpu_next_is_write(&nes->cpu)) {
    nes->cpu.rdy = false;

    bool need_alignment = (nes->cpu.cycles & 1) != 0;
    int total_dmc_cycles = need_alignment ? 4 : 3;
    uint16_t halt_addr = cpu_get_next_read_addr(&nes->cpu);

    if (cpu_next_is_sha_dummy_read(&nes->cpu)) {
        nes->cpu.ignore_h = 1;
    }

    for (int dmc_cycle = 0; dmc_cycle < total_dmc_cycles; dmc_cycle++) {
        if (dmc_cycle == total_dmc_cycles - 1) {
            /* Last cycle: actual sample read */
            uint8_t sample = nes_cpu_read(&nes->cpu, nes->apu.dmc_current_addr);
            apu_dmc_load_sample(&nes->apu, sample);
        } else {
            /* Halt/dummy/alignment cycles: re-read the upcoming bus addr */
            (void)nes_cpu_read(&nes->cpu, halt_addr);
        }
        ppu_step(&nes->ppu);
        ppu_step(&nes->ppu);
        ppu_step(&nes->ppu);
        apu_step(&nes->apu);
        nes->master_tick += 12;
    }

    if (!nes->dma.oam_active) {
        nes->cpu.rdy = true;
    }
}
```

The code runs these steps:

1. The APU signals that it needs a sample. The CPU is ready (not already halted), and its next cycle is not a write.
2. `cpu_get_next_read_addr()` returns the address the CPU was about to read. This is the halt address.
3. If this is a SHA-family dummy-read cycle, `ignore_h` is set so that the upcoming store drops the high-byte AND.
4. The DMA loop runs 3 or 4 cycles. The alignment cycle (if needed) and the dummy cycles re-read `halt_addr`, with all the side effects of that read. The final cycle reads the DMC sample.
5. Each DMA cycle also steps the PPU (3 dots) and the APU, which keeps the system synchronized.

The CPU code has no DMA logic, and the DMA code encodes no instruction timing. The generated functions give the DMA code what it needs to know about the CPU.

## DMA during the 2 writes of an INC instruction

In this sequence, the DMC needs a sample while the CPU is about to execute cycle 314 of `cpu_gen.c`. Cycle 314 is the first write cycle of an INC zero-page instruction, which writes the old value back to memory.

1. `cpu_next_is_write()` checks uPC 314 and returns true.
2. The DMA defers. The CPU executes cycle 314 and writes the old value.
3. On the next `nes_step()`, the CPU is at uPC 315, the second write (the new value).
4. `cpu_next_is_write()` checks uPC 315 and returns true again.
5. The DMA defers again. The CPU executes cycle 315, which writes the new value and sets the flags.
6. On the next `nes_step()`, the CPU is at uPC 0 (fetch).
7. `cpu_next_is_write()` checks uPC 0 and returns false, because a fetch is a read.
8. The DMA proceeds. `cpu_get_next_read_addr()` returns `cpu->PC`, the halt and dummy cycles re-read from PC, and the final cycle reads the DMC sample.

The AccuracyCoin DMA tests verify this behavior: the DMA waits through the 2 consecutive write cycles of an RMW instruction. The timing is correct because the compiler classified both cycles as writes during code generation. Nobody analyzed the INC instruction by hand, and the code has no special case for it.

## Deriving other views from one specification

This technique, deriving cross-cutting concerns from a single specification, applies outside emulation too. The timing specification and the DMA interaction rules are the same data expressed 2 ways. One view gives what the CPU does on each clock. The other gives what the bus would show if the CPU were halted on the current cycle. Both are projections of the same microcode.

The code generator must be able to classify every step statically. For the 6502 this is straightforward, because every cycle form in the DSL has exactly one bus operation. The compiler can see whether it is a read, a write or a dummy read. A CPU with dynamic bus behavior, such as conditional reads that depend on runtime state, would be harder to classify. The method still applies wherever the specification can be analyzed statically.

Interrupt timing, bus arbitration and cache coherence protocols are other cases where several subsystems must agree on behavior. Writing the authoritative specification once and deriving each subsystem's view from it removes a whole class of consistency bugs. In MyNES, a one-line change to the DSL and a compiler run update the CPU execution and the DMA interaction together. There is no separate state machine to maintain, and no comment asks the next person to update the DMA code after a timing change.

The DSL compiler is 904 lines of Scheme, and the DMA helper generation is about 100 of them. Those lines guarantee that the CPU and the DMA agree on what happens on the bus.
